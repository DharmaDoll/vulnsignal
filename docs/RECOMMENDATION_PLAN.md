# 改修計画書（2026-11-19）

## 対話での利用

日々の更新は検索用データマートに反映する。Agentが期間・技術・出来事を指定し、根拠に遡って対話で回答する。レポートは明示的なエクスポート時に保存する。[検索手順](../README.md#ローカル知識をagentから検索する)

## 実装状況（2026-11-19）

通常更新からTrivyを外し、期間別推薦と再生を `python -m scripts.period_recommendations` で利用できる。設定は [config/watch_themes.json](../config/watch_themes.json)。日次の明示的なエクスポートでは従来トリアージ結果と新方式の入力を保存し、精度評価後の切り替えに備える。[実行・比較評価の手順](REPORTS.md#期間別推薦の並行評価)

4週間の担当者評価、完了期間の月報・四半期報の代表性評価、フィード削減前後の実ネットワーク計測は運用で確認する項目。既存のTrivyミラーとシグナル履歴は保持する。取得量の計測値はPythonで受け取ったHTTP本文に限り、Git転送量は含まない。

## 目的と対象範囲

指定期間に注意すべき脆弱性を、全体および登録した注視テーマごとに推薦する。各推薦には、対象製品、期間中に変わった事実、その変化が重要な理由、出典と日付、未確認事項を示す。内部資産の照合、資産別採点、パッチキューの新規開発は凍結する。テーマの利用に資産登録は不要とする。

現行の日次レビューには、新規CVEのトリアージ、話題性を示す証拠、AIレビュー、JSONレポートがある。新規CVEの選定は初回観測日で候補を絞るため、既知CVEの重要な続報を拾う経路を加える。既存のCLIと証拠収集処理を起点とする。[日次運用仕様](REPORTS.md)

## 期間ごとの出力

| 期間 | 選定と要約の基準 |
|---|---|
| 日次 | 前回から新たに確認された実悪用、修正版公開など、その日に読む理由を示す。 |
| 週次 | 期間中の全候補を再評価し、同じ脆弱性の公告、PoC公開、実悪用確認などの経過を1件に統合する。 |
| 月次 | 単発の報道と継続・再燃した注目を区別し、重要案件の経過を出典付きで説明する。 |
| 四半期 | 代表案件と複数案件に共通する動きを選び、前四半期との差、継続して見るべきテーマ、その根拠を示す。 |

週次以上では日次掲載圏外も対象にする。各期間に全体欄とテーマ欄を設け、重複する本文は一度だけ掲載する。採用理由がなければ0件を許容し、観測不足の場合は対象フィードと欠損期間を表示する。初期案は全体の日次推薦を最大5件、週は月曜始まり、月・四半期は暦単位、タイムゾーンは設定可能とする。集計開始・終了と判断締切を明記し、進行中の期間は速報、締切済みは確定と表示する。

## 注視テーマと推薦判断

フィードは登録テーマに依存せず取得・正規化し、製品名、パッケージ名、公告本文など照合に使う証拠を保存する。全体推薦とテーマ別推薦は同じ保存済み入力から生成する。テーマの追加・変更時は対象期間の証拠をPJ内で再照合する。

テーマごとに表示名、照合語、除外語を登録し、製品・パッケージの一致と本文中の言及を区別する。JavaはJavaScriptだけの記事には一致させず、JDKやSpringを含める範囲を設定できるようにする。React利用製品の問題をReact本体の問題として掲載しない。一致理由を各テーマの推薦に添える。

重要性、話題性、新しさ、証拠の確信度を個別に記録する。公開PoC、実悪用確認、EPSSはそれぞれ意味を区別し、同じ一次情報の転載を独立した観測として数えない。候補抽出と基礎順位は明示したルールで決める。AIは保存済みの証拠を使って要約・重複整理・矛盾の指摘を行い、採否を変更した場合は元の判定、変更理由、根拠を残す。

## 実装順序と受け入れ条件

### 段階0　定期取得の棚卸しと軽量化

2026-11-19のローカル実測（Git管理領域を含むディスク使用量）はTrivy vuln-list 14 GiB、GHSA 7.0 GiB、CVE Program 4.4 GiB、Vulnrichment 2.4 GiB。4ミラーで約28 GiBを占め、別にcore.db 1.6 GiB、exploit.db 293 MiB、キャッシュ607 MiBがある。ミラーは差分更新されるため、これらは毎回の転送量を表さない。保存済み日報の8月6日・12日の2回では、ソース更新がそれぞれ331秒・146秒、DB取り込み等が132秒・73秒だった。今のフィード別所要時間と通信量は改めて計測する。11月18日まで取得記録のある主要フィードに対し、hotとTrivy vuln-listの最終試行記録は8月12日。とくにhotは推薦の中核なので、未実行と記録漏れを切り分け、鮮度を評価に含める。

| 対象 | 定期取得の方針案と検証事項 |
|---|---|
| CVE Program、KEV、GHSA、hot | 識別子と公表情報、既知の実悪用、OSSの製品・パッケージ情報、現在の注目の根拠として優先する。GHSAの取得範囲は実際に読むreviewed等のツリーとの対応を調べる。 |
| EPSS | 悪用可能性の補助指標として残す。同日再実行時は適用済みデータの日付・版を確認し、同版の全量取得と照合を省く。欠損や部分取り込みを適用済みにしない。 |
| Trivy（vuln-list、JSON、コンパイル済みDB） | 除外決定。ミラー更新、取り込み、推薦、テーマ照合、個別調査の各経路から外す。既存履歴は過去レポートの再現用に保持する。切替後は旧DBに残るTrivy由来の正規化値も新規推薦の根拠から除く。ミラー・DBが存在しない環境で日次更新と全期間のレポート生成が完了することを確認する。 |
| Vulnrichment | CVE Programと同一出典の付加情報を比較し、重大案件の採否や根拠を変える独自項目を計測する。寄与が乏しければ定期更新から個別補完へ移す。 |
| go-exploitdb | 既定の5系統を個別評価し、同一公告・URLの再収録と、独自の初出や早期観測を区別する。独自寄与のない系統を既定値から外す。 |
| NVD、資産向けVEX | 推薦の既定取得対象に加えない。すでに任意扱いのソースは削減効果に算入しない。 |

最初に通常更新をフィード別に計時し、転送バイト、読込件数、変更件数、独自の証拠数を保存する。日次ラッパーはミラーの二重更新をすでに回避しているが、取り込み末尾と日次レポートで品質集計を2回行うため、通常経路では1回にまとめる。週報・月報・四半期報は保存済み証拠から生成し、各レポートが同じ更新を起動することを避ける。

段階1の入力保存を使い、Trivyを除いた構成を基準に、同じ締切で評価対象のソースを一つずつ除いた結果を基準構成と比較する。独自の重要案件、重要な続報の検出時刻、React・Javaの照合、修正版の根拠、期間レポートの再現性に影響がなければ既定取得から外す。差が出る場合は必要な系統・頻度に絞る。旧CVEの今期の続報も評価対象にする。時間・転送量・保存量の前後差を個別に記録し、フィード設定で元に戻せることを確認する。既存のシグナル履歴は保持する。

| 段階 | 作業 | 受け入れ条件 |
|---|---|---|
| 1. 入力の保存 | 対象期間、締切、候補集合、証拠と参照値、フィード鮮度、公表・初回観測時刻、ルール版、AI入出力、現行方式の結果を実行単位で保存する。 | DB更新後も保存済み入力から外部通信・AI再実行なしで当時の順位と理由が一致し、締切後の情報が混入しない。 |
| 2. テーマ照合 | テーマ設定と一致の根拠を段階1の記録に含める。 | テーマ未登録で取得した期間にReactを追加し、再取得なしで該当案件を抽出できる。全体推薦の順位はテーマ設定に依存しない。JavaとJavaScriptを区別し、保存した旧設定で過去の掲載結果も再現できる。 |
| 3. 日次・週次推薦 | 新規公開と既知案件の続報を候補にし、期間内の変化を統合する。再掲載時は前回との差を示す。 | 半年前のCVEの当日KEV追加を拾う。同一公告の再取得で再浮上しない。週を通じて証拠が強まった日次圏外の案件を週報に掲載できる。AI停止時も根拠付きの推薦を出せる。 |
| 4. 月次・四半期推薦 | 期間の全候補から代表案件と傾向を選び、前期間との比較可能範囲を示す。 | 各傾向からCVE・出典を追跡できる。フィード追加・欠測による件数差を脅威の増加と解釈しない。 |
| 5. 比較評価と切り替え | 既存CLIで新方式を並行運用し、同じ締切の現行方式・固定した簡易プロンプト・新方式を比較する。 | 方式名を伏せた評価結果と見逃し事例を記録し、重大な事実誤認を修正した上で既定の出力を切り替える。 |

**初回リリースの到達点**は段階3までとする。ReactとJavaを登録し、同じ保存済み証拠から日報と週報を作り、各案件の掲載理由を再現できることを確認する。

## 評価方法

日次・週次は連続4週間を評価期間の初期案とする。掲載案件のうち当時読む価値があった割合、掲載件数、重要案件の見逃し、公表から掲載までの時間を併記する。見逃しは各方式の出力とは独立に作成したKEV追加・ベンダー公告等の一覧と照合する。テーマ別の誤一致と見逃し、主張と出典の一致、同じ入力での再現性も確認する。

月次・四半期は当時の証拠が揃った完了期間を使い、代表案件の妥当性と傾向の裏づけを評価する。現在のDBだけで当時の成績を推定しない。品質の数値目標は比較基準の測定後に定める。
